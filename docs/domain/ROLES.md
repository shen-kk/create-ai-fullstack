# 角色与权限领域

## 当前能力

- 权限分为 `menu`（功能菜单）与 `action`（业务操作），并通过 `groupCode` 按模块归组。
- 菜单权限使用 `menu.<module>` 命名；操作权限使用 `<resource>.<verb>` 命名。
- 角色使用不可变、全局唯一的 `code` 作为公共标识。
- 自定义角色支持创建，以及名称、说明、权限集合编辑。
- `system=true` 的系统角色不可通过公共 API 修改。
- 提交的权限代码必须全部存在；任一权限不存在时整体拒绝。
- Prisma 模式下权限集合替换在事务中完成。
- 角色创建与修改写入审计日志，不记录敏感凭据。
- 模板不提供角色删除；系统角色不可修改，自定义角色停用时先清空权限并解除用户关联。

## 权限边界

- 读取角色、读取权限目录、创建和编辑角色均要求 `roles.manage`。
- 用户分配角色同时要求 `users.write` 和 `roles.manage`。
- 前端菜单和 403 页面只改善体验，服务端守卫是最终权威。
- Admin 路由同时检查菜单权限和页面所需的读取操作权限，防止只有菜单入口却不能读取数据。

## 新增功能时如何增加权限

1. 在 `packages/contracts/src/index.ts` 的 `permissionCatalog` 登记权限。
2. 页面需要侧边栏入口时增加 `menu.<module>`；API 操作增加 `<resource>.<verb>`。
3. 在 Admin 路由和菜单声明菜单/读取权限，在按钮处按操作权限改善体验。
4. 在 API 控制器使用 `RequirePermissions` 强制校验操作权限。
5. 添加权限允许/拒绝测试，运行种子同步数据库目录。

权限代码由版本控制、迁移与种子管理，不允许后台动态创建。系统角色升级只能通过受审查的版本发布完成。完整生命周期依据 ADR-0004。
