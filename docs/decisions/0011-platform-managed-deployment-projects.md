# ADR 0011：平台托管通用部署项目

## 状态

已接受。

## 决策

部署中心使用数据库中的“部署项目”作为构建与发布规则权威来源，不强制业务仓库提交 `aiforge.deploy.yml`。部署项目定义动态部署单元、Docker Compose 文件、服务名、迁移步骤、健康检查和环境变量要求；部署环境只绑定项目、Runner/服务器与服务资源。Git 和服务器绑定为必填，项目声明需要 SQL/Redis 时对应资源也为必填。

部署根目录属于服务器资源，而不是环境字段。环境页面不再允许在未绑定资源时填写 Git、SSH、数据库或 Redis 的兼容字段；旧数据库列暂时保留用于读取历史记录，但新建和编辑环境必须通过资源绑定。

Git 仓库保存源码、Dockerfile、基础 Compose 和数据库迁移文件。Git、SSH、SQL、Redis 与其他密钥仍由服务配置和部署环境加密管理，不进入部署项目定义。发起部署时 API 将项目定义版本、环境、资源绑定、Git 提交和所选部署单元组合成不可变执行快照，Runner 只执行该快照。

部署单元代码不再限制为 `admin`、`api`、`web`，统一校验为 `^[a-z][a-z0-9_-]{0,63}$`。当前 AIForge 全栈结构作为内置项目预设存在，其他仓库可以在后台创建自己的部署项目。

## 原因

- 同一部署中心需要管理不同技术栈和不同服务名称的项目。
- 密钥与环境差异不应提交 Git。
- 自动猜测任意仓库的构建、迁移和健康检查规则不可靠，必须由管理员确认的平台配置表达。
- 不可变执行快照保证项目配置后续修改时，历史记录仍可解释和审计。

## 兼容与迁移

现有环境的 `applications` 数据暂时保留为部署单元代码存储；迁移创建一个 AIForge 默认部署项目并绑定既有环境。API 与 Admin 逐步改用 `units` 语义，数据库物理字段重命名延后，避免破坏已有发布记录。

## 后续

独立 Deploy Worker 通过专用进程入口消费数据库中的任务快照，解决 API 自部署时执行进程被替换的问题。Worker 不属于任何业务项目的发布单元，首次由运维在可信管理节点启动，后续业务项目发布不会替换它。
