# AI 开发规范

本文件是模板项目中 AI 开发的统一规则。每次开始任务前，AI 必须先阅读根目录 `AGENTS.md`、`docs/ai/CONTEXT.md` 和 `docs/ai/PROJECT.md`，再按任务索引读取领域文档。本文档适用于后台管理、用户端、服务端及共享包。

涉及界面开发时还必须阅读 `docs/design/COMPONENT_STANDARD.md`，并以其中的组件唯一入口为准。

规范代表当前默认最佳实践。AI 如果发现更好的实现，应主动提供证据、替代方案与迁移影响；经确认并记录 ADR 后可以更新规范或使用有边界的例外，不得为了形式一致强行使用不适合的组件。

## 1. 工作流程

1. 先明确目标、边界、验收条件和是否需要新增配置。
2. 搜索现有实现、契约、组件和测试；优先复用，不建立平行抽象。
3. 涉及接口时先更新 `packages/contracts` 和 OpenAPI，再实现 API，最后接入前端。
4. 涉及数据模型、权限或状态流转时，同时更新迁移、权限种子、审计记录和 ADR。
5. 完成后运行 `pnpm check`、相关单元测试和 `pnpm template:doctor`，并更新交接文档。

AI 不得编造“已完成”的功能，不得用假数据掩盖接口未接入，也不得在本地临时搭建数据库、Redis、SSH 或部署服务来替代用户提供的真实环境。

## 2. 工程边界

- `apps/api` 是业务规则、鉴权、持久化和 OpenAPI 的唯一权威来源。
- `apps/admin` 和 `apps/web` 只能通过 API 访问数据，禁止直接访问数据库。
- `packages/contracts` 只放跨端纯 TypeScript 契约，不依赖框架和数据库。
- `packages/config` 只放共享工程配置，不承载业务逻辑。
- 页面组件和控制器保持薄；业务规则放在服务层。
- 禁止跨应用从 `src` 深层导入，禁止无解释的 `any`、`@ts-ignore` 和非空断言。

## 3. UI 与 Design System

用户端使用 Tailwind CSS + shadcn-vue 作为基础组件，VueUse Motion 负责常规过渡，GSAP 仅用于确有价值的复杂编排。视觉基准为 Apple 的克制与空间感、Linear 的高密度交互、Vercel 的清晰层级。

- 默认语言为 `zh-CN`；状态码、错误码在 API 中保持稳定英文标识，界面统一通过中文映射显示。多语言必须由模板使用者显式选择后启用。
- 颜色、字体、间距、圆角、阴影和断点必须使用 Design Token；不要在页面中随意写新的颜色或间距。
- 表单标签、输入框、下拉框、按钮和卡片保持同一高度、圆角和对齐基线；选择框文字垂直居中，并使用统一图标。
- 弹窗不得因点击遮罩关闭。弹窗头部和底部固定，只有内容区域滚动；滚动条贴近内容容器边缘，不制造上下空白区域。
- 所有按钮必须有清晰的默认、hover、focus、disabled 和 loading 状态，文字与背景保持可读对比度。
- 动画要么对同一层级内容统一添加入场动画，要么不添加；动画短、顺滑、可被 `prefers-reduced-motion` 禁用。
- 反馈统一使用全局 Toast/Alert；错误必须说明下一步操作。图标使用统一线性风格，侧边栏按功能分组。
- 所有交互支持键盘操作、可见 focus、正确 label/aria 属性和足够的颜色对比度。

## 4. 状态、错误与权限

- 页面不得依赖静态假数据；加载、空状态、失败、重试和无权限状态都必须显式设计。
- 边界输入先校验，API 返回稳定错误码和中文可映射消息，不暴露堆栈、密钥或数据库详情。
- 新增功能必须同步权限目录、角色编辑界面、默认角色种子、前端菜单和审计日志。
- 后台管理员以手机号登录，邮箱只是资料字段；用户端能力只有在初始化时选择后才生成并显示。

## 5. 配置与安全

- PostgreSQL、Redis、对象存储、短信、邮件、支付、SSH 等运行时服务从环境变量或后台加密配置读取，仓库禁止提交真实值。
- 模板默认使用真实 PostgreSQL + Prisma；不得恢复 memory 模式或静默假数据回退。
- 新增环境变量必须加入 `.env.example` 并说明用途、是否必填和示例格式。
- 密钥只存密文或引用，日志、审计和错误响应不得输出密钥值。

## 6. Git、模板与发布

- GitHub `https://github.com/shen-kk/create-ai-fullstack` 是唯一主仓库。
- 新项目通过 `npm create aiforge@latest <project-name>` 选择是否启用用户端并组合代码，再通过 `pnpm run setup` 配置运行环境。头像随用户端启用；部署中心与对象存储资源库始终保留。邮件、短信、Redis 和具体服务商不得作为 CLI 业务功能；共享能力由功能依赖图自动保留。
- 模板维护者与普通项目使用相同的 `pnpm run setup`、迁移、Doctor 和启动流程，不得增加维护者专用环境文件。
- 新增可裁剪功能前必须登记唯一功能 ID、依赖和归属路径，并通过 `pnpm feature:check`；禁止在多个功能中重复拥有同一路径。
- 业务项目生成后不得把真实密钥、真实数据库或部署凭据反向提交到模板仓库。
- 发布 npm 前先确认包名、版本、README、文件白名单和 npm 登录状态；失败时如实记录。

## 7. 交付检查清单

- [ ] 契约、API、客户端、权限和文档已同步
- [ ] 无假数据、无本地基础设施替代、无真实密钥
- [ ] 默认中文、统一组件和弹窗/滚动规则已遵守
- [ ] 加载、空状态、错误、无权限和成功反馈已覆盖
- [ ] `pnpm check`、相关测试、`pnpm template:doctor` 通过
- [ ] `git diff --check` 通过；推送 GitHub `origin`
